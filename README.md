# pbre

**Protobuf reverse engineering.** Give `pbre` a binary protobuf blob with no
schema. It decodes every field into a readable tree, works out the most likely
type of each field, and can write a `.proto` file that parses the data. It is
pure Python with no runtime dependencies.

```
$ pbre capture.bin
Message {
  1 field_1: string = "Ada Lovelace"
  2 field_2: int32 = 1815
  4 field_4: Field4 {
    1 field_1: string = "555-0100"
    2 field_2: int32 = 1
  }
  4 field_4: Field4 {
    1 field_1: string = "555-0199"
    2 field_2: int32 = 2
  }
  5 field_5: double = 1234.5
  8 field_8: int32 = -42
  9 field_9: bytes = 0ac801b817  (or packed varints: [10, 200, 3000])
}

Generate a .proto file for this data? [y/N] y
Output path [message.proto] ('-' to print):
wrote message.proto
```

```proto
// Generated by pbre from 1 sample.
// Field names and types are inferred from the wire data; review them.
syntax = "proto3";

message Message {
  string field_1 = 1;  // e.g. "Ada Lovelace"
  int32 field_2 = 2;  // e.g. 1815
  repeated Field4 field_4 = 4;
  double field_5 = 5;  // e.g. 1234.5
  int32 field_8 = 8;  // e.g. -42
  // could be packed varints
  bytes field_9 = 9;  // e.g. 0ac801b817

  message Field4 {
    string field_1 = 1;  // e.g. "555-0100", "555-0199"
    int32 field_2 = 2;  // e.g. 1, 2
  }
}
```

## Install

pbre uses [Poetry](https://python-poetry.org/) and requires Python 3.12 or later.

```
poetry install           # creates a virtualenv with pbre and the dev/test tools
poetry run pbre --help
```

To install the command for everyday use, run `poetry build` and then
`pipx install dist/pbre-*.whl` (or `pip install .`). From a checkout you can
also run it with `poetry run python -m pbre ...`.

Every CI run also builds the wheel and sdist and keeps them as a
downloadable `pbre-dist` artifact on the workflow run's page in the Actions tab.

### Releases

Tagged versions are published on the repository's
[Releases page](https://github.com/jnaujok/pbre/releases) with the wheel and
sdist attached, so they can be downloaded without a GitHub login and don't
expire.

To cut a release:

1. Bump the version with `poetry version patch` (or `minor` / `major`), then
   commit and merge that change to `main`.
2. Either go to **Actions → release → Run workflow** and run it on `main`, or
   push a matching tag yourself:

   ```
   git tag v$(poetry version --short)
   git push origin v$(poetry version --short)
   ```

The **Run workflow** button tags the tip of `main` as `v<version>`, using the
version in `pyproject.toml`. It refuses to run from another branch, or if that
tag already exists. A pushed tag must match the version in `pyproject.toml`.
Either way, the workflow runs the tests, builds the package and creates the
release.

## Usage

```
pbre [decode] FILE...  [options]     # show the decoded fields (default command)
pbre proto    FILE...  [options]     # print or write the inferred .proto
pbre scan     FILE...  [options]     # find where a message starts/ends in a larger blob
```

When you don't pass a file, or pass `-`, pbre reads standard input. If several
files are given, pbre treats them as **samples of the same message type** and
infers one schema that covers all of them. More samples give better inference:
a field seen twice in any one sample becomes `repeated`, and a string field
that happens to be empty in one sample is still recognised as a string.

### Input options

| Option | Meaning |
| --- | --- |
| `-f, --format auto\|raw\|hex\|base64` | Input encoding. `auto` (the default) treats input made only of hex digits and spaces/colons as hex, and anything else as raw bytes. Base64 can be standard or URL-safe. |
| `--delimited` | Input is a stream of varint-length-prefixed messages, as written by `writeDelimitedTo`. Each message is one sample. |
| `--grpc` | Input is gRPC-framed: each message has a 5-byte prefix. Compressed frames are not supported. |
| `--skip N` | Skip N leading bytes, for example a custom header. |
| `--find-start` | (`decode`, `proto`) If the input doesn't parse from its first byte, find the most plausible start and end of the message and decode only that span. See [Finding the message in a larger blob](#finding-the-message-in-a-larger-blob). |
| `--candidate N` | (`decode`, `proto`) Like `--find-start`, but use candidate N from `pbre scan` instead of the best one. |
| `--max-field-number N` | Don't read a payload as a nested message if it uses field numbers above N. Lowering this cuts down on binary blobs being mistaken for messages. |

### Decode options

| Option | Meaning |
| --- | --- |
| `-v, --verbose` | Show the byte offset and wire type of each field, the other ways each scalar could be read (unsigned, zigzag, hex, float…), and full byte payloads. |
| `--json` | Print machine-readable JSON instead of the tree. |
| `--proto PATH` | Also write the `.proto` to PATH (`-` for stdout) without asking. |
| `--no-prompt` | Never ask about generating a `.proto`. pbre only asks when stdin and stdout are both a terminal. |

### Schema options (both commands)

| Option | Meaning |
| --- | --- |
| `-m, --message-name NAME` | Name of the top-level message (default `Message`). |
| `--package NAME` | Add a `package` line. |
| `--syntax proto2\|proto3` | Defaults to proto3. pbre switches to proto2 automatically if the data contains groups. |
| `--no-comments` | Leave out sample values and inference notes. |
| `-H, --hint PATH=TYPE[:NAME]` | Override the inferred type and/or name of a field (repeatable, see below). |

### Finding the message in a larger blob

Protobuf has no sync markers. A parse only works if it starts exactly on a
field boundary, so guessing `--skip` values one at a time rarely lines up.
When the start of your data looks wrong, run `pbre scan`:

```
$ pbre scan capture.bin
capture.bin: 14072 bytes
   #    start      end   lead  trail  fields  conf  preview
   1       12    14068     12      4      28  1.00  1: "google/protobuf/"... (32 chars)  2: "google.protobuf"  ...
   2       46    14068     46      4      27  1.00  2: "google.protobuf"  4: {3 fields}  4: {15 fields}  ...
      (same as #1 without its first field)
   ...
  decode the best candidate with: pbre decode --find-start FILE
  or pick another with:          pbre decode --candidate N FILE
```

Each row is a span `[start, end)` that parses cleanly as a message: `lead`
bytes are skipped before it and `trail` bytes ignored after it. `conf` is how
plausible the bytes in the span look, from 0 to 1. Real messages score close
to 1. Around 0.5 means the span is mostly opaque bytes fields, which is what
random, compressed or encrypted data looks like, and pbre warns about it.
pbre also points out gzip, zlib and zstd headers, gRPC frame headers and
length prefixes it finds at the start of the input.

`pbre decode --find-start` (or `pbre proto --find-start`) decodes the best
candidate and prints the span it used to stderr. If the input already parses
from its first byte, it is used unchanged. `--candidate N` picks another row
instead.

**How it works.** A real message has to end exactly on a field boundary, so
pbre works backwards from the end of the input. For every offset it parses the
single field that would start there, if any, and follows those fields forward
to see where the chain breaks. Each field is weighted by how plausible it
looks: small field numbers, minimal varint encodings, payloads that are text
or nested messages, and sensible fixed-width values score well. One
right-to-left pass covers every offset, so a scan is linear in the size of the
input (about 3 seconds per MB). Candidates are ranked by how many
plausible-looking bytes they explain.

**Limits.** A few junk bytes can form a perfectly valid field, for example
`08 05` is "field 1 = 5". When they sit directly in front of the message, the
best candidate may include them as an extra first field. That's why
alternatives are listed, and labelled when they are the same parse minus its
first fields. In tests with random junk prefixes of 1–24 bytes, the best
candidate was exactly right about 75–90% of the time, and the true start was
in the top three about 97% of the time. Real headers, with zero bytes, magic
numbers or lengths, usually fail fast and do better.

### Hints

The wire format cannot record some distinctions. For example, `int32`,
`sint32`, `bool` and `enum` are all varints, and a packed `repeated int32`
looks exactly like `bytes`. Once you know (or suspect) what a field really is,
use a hint and run pbre again:

```
pbre proto capture.bin \
  -H 1=string:name \
  -H 2=uint32:id \
  -H 4=message:PhoneNumber \
  -H 4.1=string:number \
  -H 9=int32:scores \
  -H 12=sint64:offset
```

A scalar type hint on a length-delimited field (like `9=int32` above) means
"this is a packed repeated field".

`PATH` is a dot-separated list of field numbers from the top-level message,
so `4.1` means field 1 inside the message in field 4. `TYPE` can be any
protobuf scalar type, `string`, `bytes`, `message` or `group`. `enum` isn't
accepted, because pbre can't generate the named enum type such a field needs;
use `int32` and turn it into an enum by hand. pbre ignores a
hint that contradicts the data (for example `message` on a payload that
doesn't parse as one) and says so in a comment in the `.proto`.

## How inference works

1. **Wire parsing.** The blob is split strictly into `(field number, wire
   type, payload)` records. A blob that is not a complete, well-formed message
   is rejected with the offset of the problem.
2. **Candidate interpretations.** Every length-delimited payload is checked
   to see whether it is valid UTF-8 or printable text, whether it parses as a
   nested message (pbre tries this recursively), and whether it parses as
   packed varints.
3. **Per-field decisions across all occurrences.** A field is a `string` if
   every non-empty payload is printable text. Otherwise it is a `message` if
   every payload parses as one. Anything else is `bytes`. Varints become
   `int32`/`int64` depending on range, with negative values recognised from
   their 10-byte two's complement encoding. Fixed-width values become
   `float`/`double` when every value is a plausible number, and otherwise
   `fixed`/`sfixed`. A field seen more than once in one message becomes
   `repeated`. pbre also records whether repeated scalars were packed, and
   whether zero or empty values were explicitly present, and emits
   `[packed = false]` and proto3 `optional` where needed. For input written by
   a standard protobuf library, this means the generated schema re-serializes
   the data **byte for byte**. That can't hold for input a standard library
   wouldn't produce, such as a field sent both packed and unpacked, fields
   out of number order, or overlong varints. The schema still decodes such
   input, but re-encoding normalizes it; pbre adds a note for the mixed
   packed/unpacked case.
4. **Rendering.** The tree view and JSON output use the inferred schema, so
   every occurrence of a field is shown the same way. Where pbre is unsure, it
   notes this in the output and in the `.proto`: for example, a `bytes` field
   that could be packed varints, or an int field that only ever holds `0`/`1`
   and may be a `bool`.

## Library use

```python
from pbre import analyze, render_text, generate_proto, parse_hint

decoded, schema = analyze([blob1, blob2], root_name="Person",
                          hints=dict([parse_hint("9=int32:scores")]))
print(render_text(decoded[0], schema))
print(generate_proto(schema, package="recovered"))
```

## Tests

```
poetry install
poetry run pytest
```

The tests serialize real messages with the official protobuf runtime, run pbre
over the bytes, and then compile the generated `.proto` with `grpcio-tools`.
They check that the result parses the original blob and re-serializes it
byte for byte. One of the test inputs is descriptor.proto's own
`FileDescriptorProto`, a large message with deep nesting.

## Limitations

* Field and message names cannot be recovered from the wire data. pbre uses
  `field_N` / `FieldN`; use hints or edit the `.proto` to rename them.
* Zigzag (`sint*`), `bool`, `enum`, unsigned and packed fields cannot be told
  apart from their look-alikes using the wire data alone. Use `-v` to see the
  alternatives and `--hint` to choose one.
* A short binary payload can sometimes also be a valid message. Hints or
  `--max-field-number` resolve this.
* Recursive types (a message that contains itself) are emitted as separate
  nested copies rather than one self-referencing type.
* Field numbers 19000–19999 are reserved for the protobuf implementation and
  cannot be declared in a `.proto`. If they appear in the data, pbre leaves
  them out of the schema and adds a comment saying so; parsers keep them as
  unknown fields.
* `pbre scan` and `--find-start` find one message per input (or per frame).
  They can't split several concatenated messages that have no length prefixes,
  because protobuf can't mark where one ends and the next begins.
* Maps are emitted as repeated `FieldN` messages with fields 1 and 2. Wire
  compatibility is identical, so you can rewrite them as `map<K, V>` by hand.
